Getting started

Everything here runs in your browser. There is no account, nothing is uploaded and no tracking script is loaded (see Privacy and legal). A good first ten minutes:

  1. Open the Device Lab, pick the TMP117, press Run, and read the bus log line by line.
  2. Press "Open this bus log in the Logic Analyzer" to see the same transactions as clock and data waveforms.
  3. Open the IoT Bench, click "Unplug TMP117" on the greenhouse node, and watch the dashboard and the message log react.
  4. Try the Scenario Labs in order. Each can be solved, and fails for a visible reason if you do the obvious wrong thing.

Every simulator on this site is a behavioral model: it reproduces specific, documented behavior, not the physics of a circuit. Each page lists what it leaves out, and the consolidated list is below.

Device Lab

Write JavaScript that talks I²C to a model of a real part. It runs in a sandboxed Web Worker with a time limit and no network access. The functions available to your code: 

i2c.write(addr, [bytes])        // throws on NACK
i2c.read(addr, n)               // returns [bytes]
i2c.readReg16(addr, reg)        // pointer write, then a 2-byte read
i2c.writeReg16(addr, reg, v)    // big-endian 16-bit write
i2c.scan()                      // addresses that answer
delay(ms)                       // advances simulated time, not real time
log(...values)  hex(n)  toInt16(n)
sim.set('name', value)          // change a physical input while the program runs
sim.get('name')

Each bus event is logged with a plain-language explanation. "Physical world" sliders set the starting values of the sensor's inputs, for example a temperature or a shunt current. A link such as lab.html#tmp117&code=… can place a program in the editor; it is never run until you press Run.

IoT Bench

A fleet of virtual nodes, each with a battery, one or more modeled sensors, and a link to an MQTT-style broker.

What a node does

It wakes every period, reads each sensor over a virtual I²C bus using the same register arithmetic as the Device Lab, publishes the results, and sleeps. While it sleeps the sensors keep converting and the simulated world keeps changing.

Topics and payloads

farm/greenhouse/air      {"t":60037,"seq":2,"temperature_c":17.757813}
farm/greenhouse/soil     {"t":60037,"seq":2,"ain0_v":2.399625}
farm/greenhouse/diag     {"t":60037,"seq":2,"battery_v":4.2,"awake_ms":12,"brownouts":0}
farm/greenhouse/status   online        (retained; the last-will message is "offline")

t is simulated time in milliseconds and seq counts cycles. A failed sensor adds an errors list to the diag message instead of a reading.

The broker

Follows the MQTT 3.1.1 rules for topic names and filters (+ and # wildcards, $ topics), QoS 0 and 1, retained messages and last-will messages. A client that goes silent is declared dead after 1.5 × its keep-alive, which is when its last-will is published. There is no TCP, TLS, QoS 2 or persistent session. A "link" delays or drops whole messages.

Faults you can inject

  • Drift: adds a rate (per hour) to the physical input the sensor sees, so the dashboard shows a growing gap from the true value.
  • Unplug: the part stops answering; the bus log shows a NACK and the node reports it.
  • Glitch: the part resets just before the next read. A TMP117 then reads 0x8000 (−256 °C) until its first conversion finishes; an INA219 or INA226 reads 0 A until the calibration register is written again.
  • Brown-out: the node loses power and reboots; the broker publishes its last-will and the node announces itself again.
  • Link loss and broker outage: messages are dropped; QoS 1 retries, QoS 0 does not.

The same seed replays the same run, including which packets were lost. The battery accelerator multiplies every current so a flat battery shows up in minutes; it is a teaching aid.

A page can open the Bench with settings: bench.html#preset=greenhouse&period=300&radio=ble&battery=aa2&sleep=8.

Logic Analyzer

Encoders turn transactions into digital waveforms; separate decoders read waveforms back into bytes. Both work in microseconds on edge lists, so a waveform can be generated, or imported.

  • I²C: START and STOP are SDA edges while SCL is high; 7-bit address plus the R/W bit, MSB first; ACK is SDA low on the ninth clock. Bus logs from the Device Lab and the Bench open here.
  • SPI: the four CPOL/CPHA modes, chip select active low. Decode with a different mode than the bus uses to see exactly how a wrong mode corrupts bytes. The register device is an invented teaching device, not a real part.
  • UART: start bit low, data LSB first, optional parity, stop bit(s). A receiver within about 3 % of the right rate still reads an 8N1 stream.
  • PWM and GPIO: frequency and duty measured from the edges, a hobby-servo convention (1 ms to 2 ms for 0° to 180°), and a bouncing button.

Importing a capture

Choose "Import a CSV capture" on the I²C tab. The file is read in your browser only. Expected layout:

Time [s],SCL,SDA
0,1,1
0.0000500,1,0
0.0000525,0,0
…

One row per change: time in seconds, then 0 or 1 per channel. Up to 200,000 rows and 4 MB.

Scenario Labs

Five guided problems that link the other tools together. A lab is "met" only when the model says so; progress is kept in your own browser. Each lab's logic is covered by known-answer tests that check it can be solved and that the obvious wrong answer fails.

Models

The datasheet-checked parts available in the Device Lab, the Bench and the Analyzer:

part what it is datasheet registers behaviors

How the models are checked

  1. Written in our own words. Each model describes a part's registers, addresses and formulas from its public datasheet, without copying datasheet prose or figures.
  2. Short, page-cited quotes as evidence. Every register, address and behavior carries one or more quotes of at most 15 words and the datasheet page they come from.
  3. A script checks the quotes. site/tools/verify-devices.mjs opens the vendor PDF you supply, confirms its SHA-256 and size match the model, and confirms every quote appears on its cited page. Datasheet PDFs are never copied into the repository or hosted here; the Device Lab links to the vendor's own copy.
  4. Known-answer tests. The simulator is tested against worked examples and tables printed in the datasheet (for example the INA219 and INA226 worked examples and the TMP117 temperature table), so a wrong LSB, shift or formula cannot pass silently.
  5. Derived facts are labelled. Where a behavior follows from the datasheet but is not stated in it (for example a conversion time computed from a data rate), the card says "derived".

A weaker tier exists: "driver-verified" register maps, taken from public open-source driver code at an exact commit and re-fetched by a script. Those are not simulated, are visibly labelled as weaker, and should be confirmed against the official datasheet.

The Chip Atlas and Parts catalog are built from public sources listed on those pages; the parts data is under CC BY-SA 4.0 (see its license note). Atlas and catalog entries are descriptions, not endorsements.

Formulas

Average current and battery life

I_avg = ( I_sleep × t_sleep + I_awake × t_awake + I_radio × t_radio ) / period  +  I_selfdischarge
life  = capacity × usable_fraction / I_avg
I_selfdischarge = capacity × (percent per year / 100) / 8766 h

t_awake and t_radio do not overlap, and t_sleep is what remains of the period. The radio time is the radio-on time per publish attempt, so every QoS 1 retry costs again.

Supply sag

V_supply = V_cell − I_burst × R_internal      (the node resets if V_supply drops below the MCU's minimum)

Sensor conversions (from the checked models)

  • TMP117: one count is 7.8125 m°C, two's complement; the result reads 0x8000 until the first conversion after a reset ends.
  • INA219: calibration = trunc(0.04096 / (Current_LSB × R_shunt)); shunt 10 µV per count; bus 4 mV per count after a shift of 3.
  • INA226: calibration = trunc(0.00512 / (Current_LSB × R_shunt)); shunt 2.5 µV per count; bus 1.25 mV per count.
  • ADS1115: counts are 187.5 µV down to 7.8125 µV depending on the range; one single-shot conversion takes 1 / data rate.

MQTT topic filters

+ matches exactly one level, # matches the rest and also its parent (sport/# matches sport), and neither matches a topic whose first level starts with $.

What the simulators leave out

  • Analog behavior everywhere: noise, accuracy, temperature drift of parts, rise and fall times, ringing, glitches, pull-up values and bus capacitance.
  • Real timing: the Device Lab models conversion time, not clock-edge timing; the Analyzer's waveforms have ideal edges. Nothing checks setup, hold or rise-time limits.
  • The network: path loss, collisions, TCP retransmission, TLS, reconnect storms, MQTT QoS 2 and persistent sessions.
  • Batteries: the real discharge curve, temperature and ageing. Voltage is a straight line with a fixed series resistance.
  • The MCU: its current is a number you type, not the result of running firmware.
  • Anything not listed on a model's own "leaves out" card, which is specific to that part.

A passing simulation means your logic is consistent with the documented behavior. It is not proof that real hardware works. Build, measure and test on the real board, especially for anything safety-critical.

The extension and MCP server

Aletheon itself is a VS Code extension and an MCP server that read datasheets and register maps and audit their own answers. There is no published release yet, so install it by building it from source (Node.js 20 or newer): 

git clone https://github.com/denishkarnati/Aletheon
cd Aletheon
npm install
npm run vsix
code --install-extension aletheon-0.1.0.vsix

The install section on the home page also shows how to run the MCP server. Anyone can do this: the source is public under Apache-2.0.

Contributing

Data and tests help more than code. Read CONTRIBUTING.md. To propose a new part model: write site/tools/devices/<id>.json in the same shape as the existing ones, run node site/tools/verify-devices.mjs <dir> against the vendor PDF you downloaded, run node site/tools/build-devices.mjs, add known-answer tests to site/tools/test-devices.mjs, and make sure npm run test:site passes. Questions and ideas: GitHub Issues. Please report security problems privately, as described in About and contact.
